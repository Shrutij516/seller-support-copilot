# Decisions

Single source of design decisions for Seller Support Copilot. For each component: what it
does, why we chose it, what we rejected, and the tradeoff we're accepting. Update this as we
build; don't let it drift from the code.

## FastAPI (Python 3.12)

- Status: In use
- What it does: Serves the HTTP API (health checks now, chat and seller data later).
- Why we chose it: Python is my strongest language. Bedrock, boto3, and eval tooling are Python-native. My Java is coursework-only and shallow, so a short timeline would only give me Spring Boot knowledge too thin to defend.
- Rejected alternative: Spring Boot (Java). Strong typing and ops story, but not something I can defend in depth, and it would split AI code into a second service.
- Tradeoff we accept: Weaker compile-time guarantees than Java; covered by strict mypy, Pydantic models, and tests.
- Revisit if: The API grows heavy transactional domain logic, or a Java-strong team takes over.

## Next.js static export (S3 + CloudFront)

- Status: In use
- What it does: Builds the web app to static HTML/JS/CSS, served from S3 through CloudFront.
- Why we chose it: The app is just a client of the API; no SEO or SSR need. Static hosting is near-zero cost with nothing to patch or scale.
- Rejected alternative: Next.js server on ECS Fargate. Gives SSR, route handlers, image optimization; not needed here, and costs more to run.
- Tradeoff we accept: No SSR, no `app/api`, no server actions. Each environment needs its own build since env vars are inlined at build time. The CSP also has to be a `<meta>` tag baked into each HTML file rather than a real response header, which has two consequences: `frame-ancestors` is silently ignored by browsers when delivered this way, so clickjacking protection isn't in place until a CloudFront response-headers policy adds it at the CDN layer; and `script-src` can't use a per-request nonce (no server to mint one), so Next's own inline hydration scripts are allowed via build-time SHA-256 hashes instead (`apps/web/scripts/inject-csp-hashes.mjs`, run as a `postbuild` step), not `'unsafe-inline'`.
- Revisit if: A page needs SSR for SEO, or we need server-side secrets in the front end, or the frame-ancestors gap needs closing sooner than the CloudFront setup.

## Postgres

- Status: In use (Docker locally; managed Postgres later)
- What it does: Stores relational, transactional data: sellers, orders, cases, anything needing joins or ACID transactions.
- Why we chose it: Mature, well understood, strong consistency for data that has real relationships.
- Rejected alternative: DynamoDB for everything. Would force denormalized, single-table modeling onto data that's naturally relational.
- Tradeoff we accept: Schema migrations to manage, and vertical scaling limits versus a fully managed NoSQL store.
- Revisit if: One relational table's write volume becomes the bottleneck and its access pattern is simple enough for DynamoDB.

## SQLAlchemy 2.0 + Alembic

- Status: In use
- What it does: SQLAlchemy is the typed ORM for Postgres (sellers, listings, orders, order_items, support_cases); Alembic generates and runs the schema migrations from those models.
- Why we chose it: Typed models catch column and relationship mistakes at review time instead of at a failing query in production; Alembic's autogenerate keeps migrations matched to what the models actually declare.
- Rejected alternative: Raw SQL with a thin query layer. Full control over every statement, but no typed models, and migrations would be hand-written from day one with nothing to catch drift.
- Tradeoff we accept: An ORM hides the actual SQL being run; mitigated by reading every autogenerated migration before applying it, never trusting it blindly.
- Revisit if: Query patterns get complex enough that the ORM's generated SQL becomes a real performance problem.

## Money as integer cents

- Status: In use
- What it does: `price_cents`, `total_cents`, and `unit_price_cents` store money as whole-number cents, never a float or a dollar amount.
- Why we chose it: Floats can't represent money exactly (0.1 + 0.2 isn't 0.3 in binary floating point); integer cents make arithmetic and comparisons exact, with no rounding surprises.
- Rejected alternative: Decimal/Numeric columns. Also exact, but integers are simpler to store, index, and serialize, and nothing here needs sub-cent precision.
- Tradeoff we accept: Every value needs a consistent "divide by 100" at display time; a stray raw float slipping into the codebase would silently reintroduce rounding bugs.
- Revisit if: The system needs sub-cent precision, for example currency conversion math.

## DynamoDB

- Status: In use (DynamoDB Local for dev)
- What it does: Stores chat sessions and message history.
- Why we chose it: The access pattern is simple and key-based (append a message, read a session's history by session ID, no joins), and old sessions can expire via TTL. That fits key-value better than relational tables. Honest note: at demo scale, Postgres would also work fine here; the choice is about matching the access pattern and isolating chat growth from the transactional database, not raw performance.
- Rejected alternative: Postgres tables for chat history. Works, but couples an append-only, high-churn workload to the same database handling transactional seller/order data.
- Tradeoff we accept: No cross-store transactions with Postgres. Access patterns must be designed up front since DynamoDB has no ad hoc queries, and now there are two datastores to operate instead of one.
- Revisit if: We need to join chat data with relational data in one transaction, or query needs outgrow key-based access.

## DynamoDB key design (GSI1, TransactWriteItems)

- Status: In use
- What it does: One table, two item shapes under `PK=SESSION#<id>`: a `META` item and many `MSG#<ULID>` items. GSI1 (`GSI1PK=SELLER#<seller_id>`, `GSI1SK=last_message_at`) is set only on META items, so it stays sparse: message items never populate it and never appear in it.
- Why a GSI: the table's own key answers "messages in this session," but "this seller's sessions, newest first" needs a different partition key entirely. A GSI is DynamoDB's only way to query by a second key without a full scan.
- Why TransactWriteItems: appending a message also has to bump the session's `last_message_at` (and its TTL) in the same instant. Two separate writes could land inconsistently under a crash or retry, leaving a session's "last activity" stale relative to its own messages.
- Sliding TTL: `expires_at` is 30 days from last activity, not from creation, refreshed on the META item by that same transactional write. TTL deletion is lazy (real DynamoDB can lag by hours), so reads add `FilterExpression: expires_at > now` rather than trusting the sweep to have already removed stale items.
- Rejected alternative: A second table for sessions, joined in application code. Avoids GSI sparsity concerns, but reintroduces the two-write consistency problem without any transaction guarantee.
- Tradeoff we accept: A transactional write costs roughly double the capacity of a plain write and fails the whole operation on any single conditional check; acceptable at message-append volume.
- Revisit if: Write volume grows enough that transaction cost becomes a real line item.

## SELECT FOR UPDATE vs optimistic locking

- Status: In use (`request_refund`)
- What it does: Locks the order row (`SELECT ... FOR UPDATE`) before checking eligibility and changing its status, so two concurrent refund requests for the same order serialize instead of racing.
- Why we chose it: Refund requests are rare and short-lived per order; a lock held for one small transaction is invisible to users and gives correctness for free, no retry logic needed anywhere.
- Rejected alternative: Optimistic locking (a version column, retry on conflict). Scales better under real contention, but this endpoint has none, and it would push retry handling onto every caller for a case that doesn't need it.
- Tradeoff we accept: A slow transaction holding this lock would block other refund attempts on the same order; the transaction here is just one SELECT, one UPDATE, one INSERT, so the risk is low.
- Revisit if: A single order regularly sees genuine simultaneous refund attempts, or the transaction grows to include something slower (an external API call) while the lock is held.

## Who owns the transaction

- Status: In use
- What it does: `get_db_session` is the only place that calls `commit()`/`rollback()`. It yields one session per request, commits it once the request finishes without error, and rolls back and re-raises if anything raised, domain error included. Services and route handlers (`request_refund`, `admin_update_case`, ...) just use the session they're given: no `begin()`, no `commit()`, no `rollback()`.
- Why we chose it: One unit of work per request, not one per function call. A request that touches the database in two places (say, an ownership lookup and a mutation) commits or rolls back both together. It also sidesteps a real bug this surfaced: a service calling `session.begin()` broke the moment it ran after a dependency had already queried the same session, since SQLAlchemy's `AsyncSession` autobegins a transaction on first use and `begin()` raises if one is already open.
- Rejected alternative: Each service manages its own transaction (what `request_refund` did before this). Works in isolation, breaks the instant two things share a session in one request, exactly what happened here.
- Tradeoff we accept: A service function is no longer transaction-safe on its own; calling it outside a request (a script, a test) means the caller must commit or roll back explicitly. `unit_of_work` in the test helpers exists for exactly this.
- Revisit if: A single request needs two independent, separately-committed transactions (partial success semantics) rather than one all-or-nothing unit of work.

## Cognito

- Status: Defined in CDK (6a): `infra/lib/auth-stack.ts` (`AuthStack`, us-east-1). Token verification code is in use in the API. The User Pool **isn't deployed** yet; deploying it is the owner's step after review.
- What it does: Issues JWTs with a `cognito:groups` claim (seller or admin). Authorization, what each role can actually do, is enforced in our API code, not by Cognito.
- Why we chose it: Managed auth with native AWS integration; I don't build or store passwords myself.
- Rejected alternative: Custom auth (JWT plus a users table). More code to secure and maintain for something Cognito already does.
- Tradeoff we accept: Less UI and token customization than rolling it myself; some config lives outside app code.
- Hosted-UI domain prefix: `seller-copilot-cbsn9z`, a fixed random suffix kept as `HOSTED_DOMAIN_PREFIX` in `infra/lib/auth-stack.ts`. It was generated once with a CSPRNG (`python3 -c "import secrets, string; print(''.join(secrets.choice(string.ascii_lowercase + string.digits) for _ in range(6)))"`). It follows Cognito's prefix rules: the `CreateUserPoolDomain` pattern `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$` (https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolDomain.html) and no `aws`, `amazon` or `cognito` (https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-assign-domain.html, "Reserved terms"). Jest asserts the template uses the literal constant, that it contains no `AWS::AccountId` token or 12-digit run, and that it follows the rules.
  - Rejected: an account-ID suffix (`seller-copilot-${AWS::AccountId}`). It's unique for free, but the prefix is part of every public login URL (`<prefix>.auth.us-east-1.amazoncognito.com`), so it would publish the AWS account number to anyone who sees a sign-in link.
  - Tradeoff: prefixes must be unique in the Region across all AWS customers. If someone already holds this one, the deploy fails, and a new suffix has to be generated the same way and committed.
- Revisit if: Auth needs (SSO, custom MFA) outgrow what Cognito supports cleanly.

## JWT verification in the API (not an API Gateway authorizer)

- Status: In use
- What it does: The API itself fetches JWKS, checks the RS256 signature, `iss`, `exp`, `token_use == "access"`, and `client_id`, on every request. Nothing upstream has already done this by the time a request reaches a route handler.
- Why we chose it: There's no API Gateway in front of this service yet (it runs on ECS behind an ALB); an ALB doesn't verify JWTs the way API Gateway's Cognito authorizer does. Verifying in-process also means the exact same code path is what integration tests exercise, with a locally generated key, no real AWS call required.
- Rejected alternative: An API Gateway Cognito authorizer in front of the service. Offloads verification before a request hits the API, but requires API Gateway in the stack (not currently planned) and makes the auth logic untestable without a real or emulated Gateway.
- Tradeoff we accept: Every request pays a JWKS cache lookup and a signature check in-process, and the API is the thing that must stay correct and current on token verification, not a managed layer in front of it.
- Revisit if: API Gateway gets added for other reasons (throttling, a public API surface); a Cognito authorizer there would then handle this and the API could trust a pre-verified principal header instead.

## 404, not 403, for cross-tenant access

- Status: In use
- What it does: A seller requesting another seller's order, case, or chat session gets 404. A seller calling an admin-only route gets 403.
- Why we chose it: 403 confirms a resource exists and you're just not allowed to see it; for IDs a seller might guess or enumerate (orders, cases), that confirmation is itself information leakage. 403 is the right signal only when the _route_ is restricted (admin endpoints), not when a specific resource is.
- Rejected alternative: 403 everywhere for consistency. Simpler to reason about in isolation, but wrong for owned resources: it tells an attacker "this order ID is real, you just can't have it."
- Tradeoff we accept: A seller who mistypes their own order ID sees the same 404 as one who's probing someone else's; slightly less helpful error messages in exchange for not leaking existence.
- Revisit if: A support/debugging need requires distinguishing "doesn't exist" from "not yours" in a response, which would have to go through logs, not the API response.

## Keyset (seek) pagination over offset

- Status: In use (`GET /v1/orders`; `GET /v1/admin/cases` uses the same technique on `(status, created_at, id)`, see "Admin case queue ordering" below)
- What it does: Pages on `(placed_at, id)` with an opaque cursor, instead of `LIMIT/OFFSET`.
- Why we chose it: Offset pagination shifts under concurrent writes: an order inserted between two page fetches shifts every row after it, causing skipped or duplicated results. Keyset pagination has no such window, since each page's query is "everything before this exact key," not "the Nth through Mth row."
- Rejected alternative: `OFFSET`/`LIMIT`. Familiar and simpler to implement, but gets slower on deep pages (the DB still scans and discards every skipped row) and isn't stable under concurrent inserts.
- Tradeoff we accept: No "jump to page 7," only forward paging from a cursor. Fine for an API meant to be paged through, not randomly accessed.
- Revisit if: A UI need genuinely requires arbitrary page jumps, not just "next."

## Admin case queue ordering (status, then FIFO)

- Status: In use (`GET /v1/admin/cases`)
- What it does: Default order is `status, created_at, id`, all ascending: open cases first, then in_progress, then resolved; oldest first (FIFO) within each status; id as the final tiebreaker. `case_status` is a native Postgres enum declared `open, in_progress, resolved` (see `migrations/.../95d6744ed870_initial_schema.py`), and Postgres orders native enum values by their declaration position, not alphabetically, so `ORDER BY status` already sorts by queue priority for free, no `CASE WHEN` rank mapping needed.
- Why we chose it: This is a work queue, not a feed. An admin needs open cases surfaced before resolved ones regardless of when each was touched, and within a status, the case that's been waiting longest should be handled first (FIFO), the same expectation any support queue has. `created_at` alone (the old, effectively-unordered default) puts a case resolved five minutes ago ahead of one that's been open for a week.
- Why id as the final tiebreaker: two cases can share the same `created_at` (seed data does, and a bulk import could too); without a tiebreaker, keyset pagination's "everything after this key" has no way to draw a line through a tie, and the DB is free to return them in a different order on every fetch, which can skip or duplicate rows across pages. Id is unique per row, so `(status, created_at, id)` is always a strict order, never a tie.
- Rejected alternative: Sort by `created_at` only (matches every other list in this API: orders, seller cases). Consistent with those, but wrong for this specific view: an admin's queue is triaged by urgency-then-age, not just age, and those other lists are each scoped to one seller's own items, where recency is what a seller actually wants first.
- Tradeoff we accept: A case's position in the list changes when its status changes (it moves from the open group to the in_progress group), which is correct but means "the row I was just looking at" isn't guaranteed to stay in the same spot after a background refetch; the admin UI's cache update mitigates this for the specific case being transitioned (see `apps/web/src/lib/api/hooks.ts`'s `useUpdateAdminCase`), patching it in place rather than letting an immediate re-sort happen under the cursor.
- Revisit if: The queue needs a different triage order (e.g., by case type, or a manually set priority field) that this fixed three-column sort can't express.

## application/problem+json for every error

- Status: In use
- What it does: Every 4xx/5xx response (ours, FastAPI's validation errors, routing 404s, unhandled exceptions) is RFC 9457 problem+json: `type`, `title`, `status`, `detail`, and `request_id`. Never a stack trace or raw SQL in the body.
- Why we chose it: One consistent error shape means a frontend (or this API's own future consumers) writes one error-handling path, not a different shape per failure mode. `request_id` ties a client-visible error back to a specific log line.
- Rejected alternative: FastAPI's default validation error shape for 422s, ad hoc `{"detail": "..."}` for everything else. Works, but two shapes instead of one, and nothing links a response back to server logs.
- Tradeoff we accept: A little more error-handling boilerplate (one registered handler per exception type) than just letting FastAPI's defaults through.
- Revisit if: A consumer needs `type` to be a real, dereferenceable URI per error kind rather than `about:blank`; that's the RFC 9457 extension point already there when it's needed.

## Bedrock (Knowledge Bases, Guardrails, tool calling, structured outputs)

- Status: In progress (4c). The Knowledge Base is deployed by the account owner: `KnowledgeBaseStack`, us-east-1, 6 docs ingested, 0 failed. Live Retrieve and Converse calls have been verified by hand. The answer endpoint (`POST /v1/chat/sessions/{id}/messages`) exists with fake-backed tests. `rag_min_score` is still the untuned 0.3 until the labeled retrieval eval (`make eval-retrieval`) has been run. Guardrails, tool calling and structured outputs aren't started.
- What it does: Knowledge Bases retrieve from ingested policy docs; Guardrails filter unsafe input/output; tool calling lets the model query seller/order data; structured outputs give the API typed, validated responses.
- Why we chose it: Managed retrieval and safety instead of a hand-built RAG pipeline and moderation layer.
- Rejected alternative: Self-hosted RAG with vLLM. I've built this before and know the ops cost firsthand: serving infra, a vector DB, and hand-rolled safety filtering, all first-party maintenance burden.
- Tradeoff we accept: Vendor lock-in to Bedrock's APIs and models; Guardrails add latency and per-call cost on top of the base model call.
- Answer model: Claude Haiku 4.5 through the US cross-region inference profile `us.anthropic.claude-haiku-4-5-20251001-v1:0`, set in config (`BEDROCK_MODEL_ID`), never in code.
  - Why: it's available to this account (verified with a live Converse call), it's the cheapest and fastest Claude model available here, and a grounded short answer over five ~300-token chunks doesn't need a larger one. The `us.` profile spreads load across US regions only, so requests and data stay in US geography.
  - Rejected: the `global.` inference profile. It may route requests to any commercial region worldwide, so there's no data-geography guarantee for seller questions, and a little more throughput isn't worth that here.
  - Rejected: Claude Haiku 5.5 (`us.anthropic.claude-haiku-5-5`). Live Converse returned AccessDeniedException ("not available for this account"; see Incidents). This is an account constraint, not a quality call. Revisit when it becomes available.
  - Tradeoff: an older model generation, and the inference profile's region set is AWS-managed.
- Revisit if: Retrieval quality or cost doesn't hold up under real evals.

## Retrieve + Converse, not RetrieveAndGenerate

- Status: In use (phase 4a; `src/copilot_api/rag/`)
- What it does: The chat answer endpoint makes two Bedrock calls itself: `bedrock-agent-runtime.retrieve` (top_k from settings) for policy chunks, then `bedrock-runtime.converse` with our own system prompt and the surviving chunks as numbered context. Between them, the API drops chunks below `rag_min_score`, and if none are left it stores and returns a fixed refusal without calling the model at all. Both calls sit behind small `Retriever` / `Generator` protocols injected with `Depends`, so tests swap in fakes; the Bedrock adapters are the only code that touches AWS, run via `asyncio.to_thread` on clients built once at startup, with bounded timeouts. Any Bedrock failure becomes a 503 problem+json; the user's message stays stored and no assistant message is written.
- Why we chose it: Each step we need to control or measure is ours. (1) The relevance floor and the zero-context refusal are a deterministic cost and hallucination guard: no context means no model call, which RetrieveAndGenerate can't express. (2) We own the prompt ("answer only from numbered context, cite [n], say you don't know"), so it's versioned in git, unit-tested, and the same prompt the eval harness will score. (3) Citations are built from exactly the chunks we sent, numbered to match the [n] markers, rather than parsed back out of a managed response. (4) Retrieval and generation are separately testable and separately measurable (retrieval recall vs. answer faithfulness) in the eval phase. (5) Converse is model-agnostic, so swapping models is a settings change.
- Rejected alternative: `RetrieveAndGenerate` (one managed call). Less code and Bedrock formats citations for us, but the prompt template, chunk filtering, and "skip the model when nothing relevant came back" are all out of our hands, failures are one opaque error instead of "which stage failed", and testing it means faking one big managed response instead of two small interfaces. Also rejected: calling Converse with the whole policy corpus in context (no retrieval). The corpus is only ~3k words today, so it would work now, but cost grows linearly with the corpus on every request and it trains the system away from the retrieval it will need.
- Tradeoff we accept: Two network round trips (and two failure points) instead of one, and more of our own code to maintain (prompt, citation mapping, score filtering). `rag_min_score` (0.3) is an untuned placeholder until the eval set exists: too high refuses answerable questions, too low lets weak context through. (Citations used to list every chunk sent to the model; since phase 4c they're filtered to what the answer cites. See "Citations = only what the answer cites".)
- Revisit if: Evals show RetrieveAndGenerate's managed prompt/citations matching ours on faithfulness at lower latency, or we need Bedrock features only available through it.

## S3 Vectors as KB vector store

- Status: Defined in CDK (`infra/lib/knowledge-base-stack.ts`, phase 4b); not deployed yet.
- What it does: An `AWS::S3Vectors::VectorBucket` plus one `AWS::S3Vectors::Index` (1024 dims, cosine, float32) is the Knowledge Base's storage (`S3_VECTORS`). `AMAZON_BEDROCK_TEXT` and `AMAZON_BEDROCK_METADATA` are declared non-filterable at index creation, because Bedrock writes the chunk text and its metadata blob into every vector and both exceed the filterable-metadata size limit (and the setting can't be changed after creation).
- Why we chose it: Pay-per-use with no cost floor: storage plus per-request charges, nothing running when idle. For ~3k words of policy (tens of chunks) at portfolio traffic, that's effectively free, and it's fully managed (no cluster, no schema, no capacity). Bedrock KB supports it natively, so nothing else changes in the RAG code.
- Rejected alternative: OpenSearch Serverless, the classic KB default. Its minimum OCU footprint bills around the clock whether or not anyone queries, by far the largest line item in this project for a corpus this small. Also rejected: pgvector on our existing RDS Postgres, which avoids a new service but means owning a vector schema, an embedding-dimension migration story, index tuning, and Data API/Secrets Manager wiring for Bedrock to reach it, plus it couples the KB's availability to the transactional DB.
- Tradeoff we accept: Higher, less predictable query latency than an in-memory ANN index, fewer search features (no hybrid/keyword search, limited filtering), and a younger service with less community knowledge. Dimension and distance metric are fixed at index creation; changing embedding models means a new index and a full re-ingest.
- Revisit if: Retrieval latency becomes the dominant part of answer latency, or evals show we need hybrid (keyword + vector) search.

## Titan Text Embeddings V2

- Status: Defined in CDK (phase 4b); not deployed yet.
- What it does: `amazon.titan-embed-text-v2:0` at 1024 dimensions (FLOAT32) embeds policy chunks at ingestion and queries at retrieval time.
- Why we chose it: Native to Bedrock in us-east-1 (where the API runs), cheap per token, and 1024 dims is its full-quality setting while still small for S3 Vectors. English-only policy text doesn't need a multilingual model. One model ARN means the KB role's `bedrock:InvokeModel` grant is a single exact resource.
- Rejected alternative: Cohere Embed v3 (English or multilingual). Competitive quality, but higher cost per token with no benefit we can show yet, and no multilingual need. Also rejected: Titan V2 at 256 or 512 dims, which saves storage that's already negligible at this corpus size, at some recall cost.
- Tradeoff we accept: Locked to 1024 dims in the index; switching models or dimensions is a new index plus a full re-ingest, not a config change. Quality is unmeasured until the eval set exists.
- Revisit if: Retrieval recall in evals is weak and a different embedding model measurably fixes it.

## Docs upload via aws s3 sync, not BucketDeployment

- Status: In use (`make kb-upload`; ingestion via `make kb-ingest`). Neither target is run by CI.
- What it does: `kb-upload` reads the docs bucket name from the stack outputs and runs `aws s3 sync data/policies s3://<bucket>/ --delete` (Markdown only), making the bucket mirror the repo. `kb-ingest` starts an ingestion job, polls until COMPLETE/FAILED/STOPPED, prints the job statistics, and exits non-zero unless COMPLETE.
- Why we chose it: Content changes and infra changes are different operations with different review needs. Editing a policy doc shouldn't require a CloudFormation deploy, and a deploy shouldn't silently rewrite the corpus. `sync --delete` is idempotent and keeps "what's in git" equal to "what's in the bucket", so a deleted doc also leaves the KB on the next ingest. Both steps call real AWS, so they stay explicit, manual commands.
- Rejected alternative: `aws-s3-deployment.BucketDeployment`. It works, but adds a Lambda function, a Lambda layer with the AWS CLI, an assets bucket, and a custom resource, all with their own IAM (including broad S3 permissions), just to copy six Markdown files. It also re-uploads on every deploy and still doesn't trigger ingestion. Also rejected: `autoDeleteObjects`, a similar custom-resource Lambda that empties the bucket on stack deletion; emptying the bucket is a deliberate manual step instead.
- Tradeoff we accept: Two extra manual commands after deploy (and after any doc change), and stack deletion fails until the docs bucket is emptied by hand. The bucket can drift from git if someone uploads directly; the next `kb-upload` resets it.
- Revisit if: Docs change often enough that a CI job should upload and ingest on merge to main (with its own narrowly scoped role).

## KB role scoping + confused-deputy conditions

- Status: Defined in CDK (phase 4b), enforced by `infra/test/knowledge-base-stack.test.ts`.
- What it does: The KB service role trusts only `bedrock.amazonaws.com`, and only when `aws:SourceAccount` is this account and `aws:SourceArn` matches `arn:aws:bedrock:us-east-1:<account>:knowledge-base/*`. Its one inline policy grants `s3:ListBucket` on the docs bucket and `s3:GetObject` on its objects (both also conditioned on `aws:ResourceAccount`), `bedrock:InvokeModel` on the Titan V2 model ARN only, and the five S3 Vectors actions AWS documents for KB ingest and query (`PutVectors`, `GetVectors`, `DeleteVectors`, `QueryVectors`, `GetIndex`; source: https://docs.aws.amazon.com/bedrock/latest/userguide/kb-permissions.html#kb-permissions-s3vectors) on that one index ARN. Tests fail on any Allow statement with `Action: "*"`, a service wildcard (`s3:*`), or `Resource: "*"`.
- Why we chose it: The source conditions stop the confused-deputy case, where another account's Bedrock resource gets our role used on its behalf. Exact-ARN grants mean a misconfigured data source or a compromised KB can read only these docs and write only this index. The policy is inline on the role (not a separate `AWS::IAM::Policy`), so it exists before CloudFormation creates the KB, which checks the role's access at creation time.
- Rejected alternative: The policy in AWS's own KB permissions doc, which also grants `bedrock:ListFoundationModels` and `bedrock:ListCustomModels` on `Resource: "*"`. Those are for the console's model picker, not for ingesting or querying with a fixed model ARN, so we leave them out. Also rejected: pinning `aws:SourceArn` to the exact KB id. That's circular in one stack (the role must exist before the KB, so the KB id isn't known yet) and would need a second deploy step to tighten.
- Tradeoff we accept: `knowledge-base/*` in the trust condition allows any KB in this account and region to assume the role, not just ours. `s3:GetObject` needs the bucket's `/*` object ARN (scoped to this one bucket, not a global wildcard). The bucket policy that `enforceSSL` adds is a Deny on `s3:*`; the wildcard test exempts exactly that Deny (it narrows access) and checks it's present. If Bedrock ever needs an action not on AWS's list, ingestion will fail with AccessDenied until we add it deliberately.
- Revisit if: We add a second KB or data source, or tighten `aws:SourceArn` to the KB id with a post-deploy update.

## Scoped CloudFormation execution policy instead of default AdministratorAccess bootstrap

- Status: Written and tested (phase 4c-pre: `infra/bootstrap/cfn-exec-policy.json`, `infra/bootstrap/README.md`, `infra/test/cfn-exec-policy.test.ts`). Not yet created in IAM, and the account isn't bootstrapped. `make deploy-policy-create` and `make cdk-bootstrap` are run by hand after review.
- What it does: `cdk bootstrap --cloudformation-execution-policies <copilot-cfn-exec ARN>` gives the bootstrap's CloudFormation execution role only the actions needed to create, update and delete the resource types in `KnowledgeBaseStack`. That's 67 actions taken from those types' CloudFormation handler permission lists, plus `ssm:GetParameters` on the CDK bootstrap version parameter, which CloudFormation resolves with this role at change-set time (added after the first deploy failed; see Incidents). Each is scoped to the stack's resources:
  - IAM to `arn:aws:iam::<account>:role/KnowledgeBaseStack-*`, with `iam:PassRole` allowed only when passing to `bedrock.amazonaws.com`
  - S3 to `knowledgebasestack-*` buckets
  - S3 Vectors to the stack's one vector bucket and index, by exact ARN
  - Bedrock to knowledge bases in us-east-1

  Every statement requires `aws:RequestedRegion = us-east-1`. The only `Resource: "*"` is `bedrock:CreateKnowledgeBase`, which has no resource-level permissions according to the Service Authorization Reference.
- Why we chose it: The default bootstrap attaches `AdministratorAccess` to the execution role. Anyone who can get CloudFormation to deploy a template in this account, through the CDK deploy role, a compromised CI credential or a malicious construct, then has full admin, including creating IAM users and roles with any permissions. With this policy, the worst a bad template can do is create, change or delete a `KnowledgeBaseStack-*` role passable only to Bedrock, a `knowledgebasestack-*` bucket, S3 Vectors resources, or a Bedrock KB, all in one region. The test suite makes widening visible: wildcard actions, unscoped IAM, `PassRole` without its service condition, a missing region lock, or an unreviewed resource type in the stack each fail CI.
- Rejected alternative: The default `AdministratorAccess` bootstrap. Zero friction, but it turns "can deploy a CloudFormation template" into "is account admin". Also rejected: AWS managed service policies (`AmazonS3FullAccess`, `AmazonBedrockFullAccess`, `IAMFullAccess`). They're simpler to attach, but each is `service:*` on `*`, and `IAMFullAccess` alone is privilege escalation to admin. Also rejected: a permissions boundary on top of `AdministratorAccess`. It's a valid pattern, but the boundary would need the same careful scoping as this policy, plus the admin grant still sitting underneath it.
- Tradeoff we accept: Every new resource type, or new property that needs a new API call, makes the first deploy fail with AccessDenied and roll back until this policy is widened. The policy is derived from published handler lists, not observed from a real deploy, so the first deploy may still surface a missing permission. Also:
  - **Explicit vector names:** `KnowledgeBaseStack` names its vector bucket `seller-copilot-kb-vectors` and its index `seller-policies`. CloudFormation's generated vector names have no documented prefix, so without explicit names the policy could only cover every vector bucket in the region. With them, the S3 Vectors statements grant on those two exact ARNs. The cost: **one stack per account and region**, since vector bucket names are unique there and a second copy would collide. Also, these resources can't be replaced in place, so a new dimension or metric means a new index name plus a policy update in the same diff.
  - **No account wildcards:** every ARN's account field is an `{{ACCOUNT_ID}}` placeholder. IAM policy variables like `${aws:PrincipalAccount}` aren't allowed before the fifth colon of an ARN, which is where the account field is. `make deploy-policy-*` renders the caller's account into a temp file at create time, so the account ID is never committed. The cost: the committed JSON isn't directly usable with `aws iam create-policy`; it has to go through the Makefile, and the test checks it renders cleanly.
  - **Shared execution role:** the bootstrap is per account and region, so `BudgetStack` can no longer be deployed through it (it was always a manual deploy).
- `AuthStack` (phase 6a): widened by 22 `cognito-idp:` actions taken from the four Cognito resource types' handler permissions. 20 are scoped to `arn:aws:cognito-idp:us-east-1:{{ACCOUNT_ID}}:userpool/*`; `CreateUserPool` and `DescribeUserPoolDomain` are on `*`, because the Service Authorization Reference lists no resource type for them. KMS, IAM role and CloudFront handler actions are excluded (no CMK, SMS role, Lambda trigger or custom domain). Tests cover the actions, their scope and `AuthStack`'s resource types. See `infra/bootstrap/README.md`, "AuthStack (Cognito)".
- Future stacks: **any new stack, resource type or property that needs a new permission must widen this policy explicitly in a reviewed diff.** That means updating `cfn-exec-policy.json`, the README's sources and exceptions, and `REVIEWED_RESOURCE_TYPES` in the test, then running `make deploy-policy-update`. Falling back to `AdministratorAccess`, even "temporarily", isn't an option.
- Revisit if: We add several stacks with very different needs (then one execution policy per bootstrap qualifier), or move deploys to CI (then the CI role's own permissions need the same review).

## Retrieval threshold from a labeled set, not a guess

- Status: In use (phase 4c). Tooling: `evals/retrieval_golden.jsonl`, `evals/calibrate_retrieval.py`, `make eval-retrieval`. The value picked from it, 0.55, is recorded in "Relevance floor is a cost guard, not the refusal mechanism".
- What it does: 20 in-scope questions, each labeled with its expected source doc and key fact, and 10 out-of-scope questions (general knowledge, other platforms, nonsense, seller-sounding look-alikes) go through the live KB with the same retriever the route uses. The script reports hit@1 and hit@5, the top-score distributions for both classes, and the highest threshold that keeps at least 95% of in-scope questions answerable, along with how many out-of-scope questions that threshold refuses. The threshold is computed on each question's top score, because the route refuses exactly when the top chunk is below `rag_min_score`.
- Why we chose it: The relevance floor decides two failure modes at once: refusing questions the docs answer (too high) and sending off-topic context to the model (too low). The original 0.3 was a guess, and a live spot check already shows it's wrong. On-topic top scores were 0.64–0.69 and "What is the capital of France?" scored about 0.52, so 0.3 lets nearly everything through. A labeled set turns the choice into a measured tradeoff that can be re-run whenever the embedding model, chunking or corpus changes, and leaves a results file to point to.
- Rejected alternative: Hand-picking a value from a few spot checks (e.g. "0.55 looks right"). Quick, but unrepeatable and blind to how close the classes are. Also rejected: relying on the model to say "I don't know" with no floor. That pays for a model call on every off-topic question and trusts the prompt alone to resist irrelevant context.
- Tradeoff we accept: 20 in-scope questions is a small sample. "≥95% kept" means losing at most one, so the threshold is only as reliable as the score gap in this sample. The same author wrote the policies and the questions, which likely inflates in-scope scores (see `evals/README.md`). The script uses a top-score threshold only; it doesn't measure answer quality.
- Revisit if: Real seller questions exist (replace or extend the set), the classes overlap so much that no threshold separates them (then consider a reranker or query classification), or the embedding model or chunking changes.

## Citations = only what the answer cites

- Status: In use (phase 4c; `filter_cited` in `src/copilot_api/rag/prompt.py`, applied in `rag/pipeline.py`, which the route, `scripts/rag_smoke.py` and `evals/answer_eval.py` all call).
- What it does: After Converse returns, the answer text is parsed for citation markers: `[n]`, adjacent `[2][3]`, or `[1, 2]`. Only citations whose index appears are returned and stored, with their original numbers, so markers in the text still point at the right source. Out-of-range numbers are ignored, duplicates collapse to one, and an answer with no markers (a refusal, or an uncited reply) gets zero citations.
- Why we chose it: Live smoke runs showed the old behavior misleading in both directions. A refund answer cited only `[3]` but returned five citations, implying four sources it didn't use. A correct "I don't know based on the marketplace policies" refusal for an off-topic question still came back with five citations, which looks like the system found something. A citation should mean "this sentence came from here". Filtering also makes citations scorable: the answer eval checks that the expected source is among the cited ones.
- Rejected alternative: Returning all retrieved chunks (the 4a behavior). Simple and never "loses" a source, but it overstates grounding and contradicts refusals. Also rejected: asking the model for structured JSON citations. That's more robust than parsing text, but it's a larger prompt and response contract to build and test, and it's unnecessary while the plain `[n]` convention works.
- Tradeoff we accept: This relies on the model actually emitting `[n]` markers in the instructed format. An answer that's grounded but uncited (or cited as "(source 2)") shows no citations, and a marker the model invents for a real chunk number is trusted. The answer eval counts a missing expected citation as a failure, so drift in citation behavior shows up in `make eval-answers`.
- Prompt rule added after the first live answer eval (in-scope 20/20, out-of-scope 7/10): "If the context does not answer the question that was asked, say so briefly. Do not offer related information instead, and do not cite anything." Two out-of-scope failures were the model refusing but still citing a tangential chunk (sourdough cited listing rules), or declining the Amazon FBA question and then volunteering Kestrel's own fees with a citation. The scorer and refusal pattern were left unchanged. Rejected: post-filtering citations on answers that look like refusals. That would hide the behavior instead of fixing it, and needs a refusal classifier in the request path.
- Revisit if: The eval shows frequent grounded-but-uncited answers. Then switch to structured citations or Converse's native citation support.

## Answer eval: deterministic scoring, no LLM judge

- Status: Tooling in place (phase 4c): `evals/answer_eval.py`, `make eval-answers`. The first live run is next.
- What it does: Runs all 30 golden questions through the production pipeline (`answer_question`) and scores each one deterministically:
  - **In-scope passes** when every golden `key_terms` entry appears in the answer (case, whitespace, quote and dash style ignored; citation markers stripped first; numbers matched as whole numbers) and at least one returned citation is from the expected source doc.
  - **Out-of-scope passes** when the answer has zero citations and matches a documented refusal regex.

  It also reports Converse token usage and an estimated cost from the Bedrock pricing page (Haiku 4.5, Geo on-demand, us-east-1).
- Why we chose it: Reproducible, free beyond the Bedrock calls, and every failure has a concrete, inspectable reason ("key terms not found: ['30']", "no citation from fees.md"). At 30 questions, a human can read every failure anyway.
- Rejected alternative: An LLM-as-judge for correctness and faithfulness. It handles paraphrase and partial answers better, but adds a second model's cost and variance, needs its own calibration, and blurs "what failed" into a score. Worth adding once the set is larger.
- Tradeoff we accept: Term matching is brittle. A correct answer phrased differently ("a month" for "30 days") fails, and an answer that contains the right number in a wrong sentence passes. The refusal regex can miss unusual refusal phrasing. Each failure is printed in full so these cases are visible rather than silently counted.
- Token accounting: `Generator.generate()` returns a `Generation(text, input_tokens, output_tokens)` per call. `answer_question` puts that call's usage on `RagAnswer`, and the eval and smoke script sum it. Rejected: the first version accumulated running totals on `BedrockConverseGenerator`. That generator is an app-wide singleton shared by concurrent requests, so the counters were shared mutable state that nothing in the request path should own. A unit test now asserts the generator has no such attributes.
- Revisit if: The golden set grows past what a person can read through, or term-matching false failures become common.

## Policy docs avoid markdown tables (chunking experiment)

- Status: Decided (phase 4c). The experiment confirmed the prediction, and all three tables are now bullet lists. `services/api/tests/unit/test_policy_docs.py` fails if any file in `data/policies/` has a line starting with `|`.
- What it does: Tests whether markdown tables cause the whole-file results (the original hypothesis was that tables stop Bedrock's FIXED_SIZE chunker, at 300 tokens and 20% overlap, from splitting a document; see the mechanism correction under Decision). In the baseline retrieval run (`evals/results/retrieval-2026-10-29.json`), the three policy files that contain a markdown table came back as one chunk each: `account-health.md` about 662 tokens, `fees.md` about 608, `shipping-and-delivery-slas.md` about 718. The three without a table came back as 3 chunks each, at most about 310 tokens. In `fees.md` the only table (referral fee by category) is converted to a bullet list with the same rows and numbers; nothing else changes. `account-health.md` and `shipping-and-delivery-slas.md` keep their tables as the control group.
- Prediction: after `make kb-upload` and `make kb-ingest`, `fees.md` goes from 1 chunk to about 2–3, and the two control files stay at 1. If `fees.md` stays at 1, tables aren't the cause and the hypothesis is rejected.
- Why we chose it: A whole-file chunk dilutes the embedding (one vector for six topics) and sends ~700 tokens of mostly irrelevant context to the model. A one-file, one-variable change with a control group gives a causal answer, not just a correlation across six files.
- Rejected alternative: Converting all three files at once (no control, so a re-ingest artifact couldn't be told apart from a real effect). Also rejected: switching chunking strategy (semantic or hierarchical) before knowing the cause. That changes many variables at once and costs a full re-ingest anyway.
- Tradeoff we accept: The fees doc reads slightly worse as a list than as a table, and the result is from one KB snapshot with approximate token counts (words × 1.33).
- Result (`evals/results/retrieval-2026-10-29-02.json`, owner's run after re-upload and re-ingest): **prediction confirmed.**
  - `fees.md`: 1 chunk (~608 tokens) → 3 chunks (max ~257).
  - Controls unchanged: `account-health.md` 1 chunk (~662), `shipping-and-delivery-slas.md` 1 chunk (~718).
  - Retrieval quality unchanged: hit@1 95%, hit@5 100%.
- Decision: **Policy docs avoid markdown tables, because for `.md` pages that contain a table, Retrieve returned the whole page instead of the matching chunk.**
  - Mechanism, corrected after the fact: Bedrock did chunk these files. Its chunking guide says that for markdown content, when a page contains a table, Bedrock can attach the full page or table text (up to 10,000 characters) to each chunk from that page. At retrieval, a matching chunk is replaced with that broader context, and chunks sharing it are returned as a single result. Source: https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html#kb-chunking-tables-figures. The experiment established that tables were the cause; the docs explain how.
  - The two control files' tables are converted to bullet lists with the same facts and numbers. Every golden key term and expected-fact number for their questions (in-11 to in-17) is still present verbatim.
- Rejected alternative: switching the data source to hierarchical or semantic chunking. Either might handle tables, but it changes how every file is split at once and hides the cause. The measured problem was specific to tables, and the fix is a content rule we can test.
- Tradeoff we accept: Authors must write tabular facts as lists, which reads a little worse for genuinely tabular data (fee schedules, score bands). The rule is enforced by a test, not a style note. If the corpus ever needs real tables, the chunking strategy decision comes back.
- Revisit if: Tabular content becomes common enough that lists hurt readability, or Bedrock's default parser changes how it handles tables (re-run the experiment: one file, one control).

## Relevance floor is a cost guard, not the refusal mechanism

- Status: In use (phase 4c). `rag_min_score` default is 0.55 in `config.py` and `.env.example`, pinned by `tests/unit/test_rag_settings.py`.
- What it does: Chunks below 0.55 are dropped. If none are left, the API returns the fixed refusal without calling the model. Above the floor, deciding whether the context actually answers the question is the model's job, through the system prompt rule "If the context does not answer the question that was asked, say so briefly. Do not offer related information instead, and do not cite anything."
- Why we chose it:
  - **Separate classes don't exist at the score level.** In `evals/results/retrieval-2026-10-29-02.json`, in-scope top scores run 0.584–0.787 and out-of-scope 0.511–0.754. The off-topic "Does Kestrel Market collect sales tax...?" (0.754) outscores 18 of 20 real questions. No threshold separates the classes, so the floor can't be the refusal mechanism.
  - **The prompt rule already does the refusing.** With the floor at 0.3 the answer eval refused 8/10 out-of-scope questions with zero citations, and the remaining two were safe non-answers the pattern doesn't recognize.
  - **0.55 costs no real question.** It keeps 20/20 in-scope (lowest in-scope top score 0.584, in-19) and still skips the model entirely for the 4 clearly unrelated questions (out-01, -02, -03, -08, top scores 0.511–0.533).
- Rejected alternative: 0.614, the calibration script's "keep ≥95% in-scope" value. It refuses 1 of 20 real questions (in-19, the paraphrased refurbished-laptop photo question at 0.584), and in this sample refuses exactly the same 4 out-of-scope questions as 0.55. So it costs a real answer and buys nothing. Also rejected: keeping 0.3, which lets every question through, including keyboard mash.
- Tradeoff we accept: Most off-topic questions (6/10 here) still reach the model and rely on the prompt to decline. At about 2,000 input and 70 output tokens per question (answers eval: 60,756 / 2,056 tokens over 30 questions), each costs roughly $0.003 at Haiku 4.5's Geo on-demand price. That's an estimate, and abuse at volume is a rate-limiting problem, not a threshold one. The margin under the weakest real question is thin (0.584 vs 0.55), and 20 author-written questions is a small sample.
- After hierarchical chunking (`retrieval-2026-10-29-04.json`): **kept at 0.55.** The lowest in-scope top score rose to 0.621 (from 0.584), so the margin under the weakest real question widened. Rejected: re-tuning the floor upward to the new numbers. On a 30-question, author-written set, chasing each run's minimum is overfitting, and the floor is a cost guard, not the refusal mechanism, so a little extra headroom costs nothing.
- Revisit if: Real seller questions arrive (re-run the calibration on them), the embedding model or chunking changes, or the answer eval's out-of-scope refusals regress (the prompt is doing the work, so that's where to look first).

## Hierarchical chunking

- Status: In use. Deployed by the account owner and verified live (2026-10-29); results below.
- What it does: `KnowledgeBaseStack`'s data source switches from FIXED_SIZE (300 tokens, 20% overlap) to HIERARCHICAL: parent `maxTokens` 1000, child `maxTokens` 150, `overlapTokens` 30. Bedrock embeds and matches the small child chunks. At retrieval it replaces each matched child with its parent chunk, so the model gets the surrounding section rather than a 300-token slice. Our policy docs are about 500–720 words (roughly 700–950 tokens), so a parent is close to a whole document.
- Why we chose it: The fixed-size split regressed in-scope answers from 20/20 to 18/20 (see Incidents, "Fixed-size chunking split facts across chunks"). in-09 lost "returns the referral fee" to an unretrieved neighbor chunk, and in-15's fact-bearing intro chunk wasn't retrieved at all. Small children give precise matching (a 150-token chunk about "order defect rate" embeds close to that question), and the parent returns the whole fact with its context. That's the 20/20 behavior we had when files came back whole, without the oversized-embedding problem.
- **AWS caveat, stated plainly:** the Bedrock chunking guide says "Hierarchical chunking is not recommended when using S3 vector bucket as your vector store. When using high number of tokens for chunking (over 8000 tokens combined), you may run into metadata size limitations." (https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html#kb-hiearchical-chunking). The S3 Vectors docs explain that parent and child relationships and hierarchical context are stored as non-filterable metadata (https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html#s3-vectors-bedrock-kb-limits), and the limit is 40 KB total metadata per vector (2 KB filterable) (https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-limitations.html). Our combined 1,150 tokens is about 14% of the 8,000-token warning level. A 1,000-token parent is roughly 4–5 KB of text, well under 40 KB. `AMAZON_BEDROCK_TEXT` and `AMAZON_BEDROCK_METADATA` are already non-filterable on the index. A Jest test keeps combined tokens at or below 2,000. If ingestion reports metadata-size failures, this is the first suspect.
- Replacement behavior: `ChunkingStrategy` and `HierarchicalChunkingConfiguration` are "Update requires: Replacement" (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-bedrock-datasource-chunkingconfiguration.html, https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-bedrock-datasource-hierarchicalchunkingconfiguration.html). CloudFormation creates the new data source, then deletes the old one (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-bedrock-datasource.html). So:
  - **Name:** renamed `policies-s3` → `policies-s3-hierarchical`, so the two can coexist during that window in the same KB. The logical ID stays `DocsDataSource`, so the `DataSourceId` output and `make kb-ingest` follow the new one.
  - **`dataDeletionPolicy: DELETE`, set explicitly** (it's "No interruption" to change and is also the documented default). When the old data source is deleted, Bedrock deletes its vectors from the shared S3 Vectors index (https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html#s3-vectors-bedrock-kb-manage-sync). With RETAIN, the old 300-token chunks would stay in the same index and keep being returned alongside the new ones.
  - **Consequence for the owner:** between the deploy finishing and `make kb-ingest` completing, the new data source has no vectors and the old ones are gone. Retrieval returns nothing, and chat answers fall back to the refusal. Run `make kb-ingest` right after the deploy.
  - **Permissions:** the CloudFormation execution policy already allows Create, Get, Update and DeleteDataSource and GetKnowledgeBase on the KB ARN, which is everything the `AWS::Bedrock::DataSource` handlers need without KMS. A new Jest test pins that. Bedrock deletes the old vectors with the KB service role, which already has `s3vectors:DeleteVectors`.
- Retrieval side effect: because child matches are replaced by their parents, and children of the same parent collapse into one result, Retrieve can return **fewer than `numberOfResults` (top_k=5)** chunks. The chunking guide says: "the returned number of results might be less than the requested amount". Nothing in the pipeline assumes exactly five. The retrieval eval's hit@5 now means "within whatever came back".
- Rejected alternative: larger fixed chunks (e.g. 600–800 tokens). That fixes boundary splits by making chunks almost whole docs, but each embedding then mixes several topics again, the precision problem the table fix removed. Also rejected: semantic chunking. It costs a foundation-model call at ingest, its boundaries are opaque and can still split a fact from its qualifier, and it changes how every file is split in a way that's hard to reason about. Also rejected: pre-splitting docs by section into separate files with NONE chunking. Precise and fully under our control, but it makes the corpus layout an ingest artifact, multiplies files to maintain, and needs a tested splitter.
- Tradeoff we accept: each retrieved result is a whole-document parent (~577–745 tokens) instead of a ~300-token chunk, and we accept AWS's "not recommended with S3 Vectors" caveat at a deliberately small token size. The entry originally predicted "roughly 2–3x the per-question cost"; measured input tokens actually went **down** (see results). That prediction was wrong; see the fixed-size incident's "What each reviewer missed".
- Measured results (owner's live runs, exact output verified by the reviewer):
  - **Deploy:** CloudFormation replaced the data source (the change set showed `Replacement=Conditional`). New data source `AUKZILCLZK` (`policies-s3-hierarchical`); old `NXNCY57HMT` is gone.
  - **Old vectors purged** (`dataDeletionPolicy: DELETE` worked): grepping `list-vectors` metadata for `NXNCY57HMT` found 0 vectors; the positive control `AUKZILCLZK` found 36.
  - **Ingest:** 6 documents indexed, 0 failed. No S3 Vectors metadata-limit failures.
  - **Retrieval** (`evals/results/retrieval-2026-10-29-04.json`): source-level and fact-level hit@1 95%, hit@5 100%. No question had the right doc without a fact-bearing chunk. Lowest in-scope top score 0.621 (was 0.584). Every source returns exactly 1 distinct parent, ~577–745 tokens, i.e. the whole document. Retrieve returned 1–5 results per question, mean 2.57 (fewer than top_k, as documented).
  - **Answers** (`evals/results/answers-2026-10-29-04.json`, `rag_min_score` 0.55): in-scope **20/20** (in-09 and in-15 fixed), out-of-scope 9/10. The one miss, out-07, is the known scorer limitation: a safe refusal with zero citations, worded outside the regex. Tokens: 51,606 input / 1,907 output, estimated $0.0673 for 30 questions (about $0.0022 per answer).
- What this shows: every policy doc is under the 1,000-token parent size, so **parents are whole documents**. Here the benefit is precise child matching (a 150-token chunk embeds close to its question) plus whole-document context for the model, with no fact cut off at a boundary. With docs this short, that's close to "retrieve whole docs, ranked by their best paragraph". The advantage over fixed-size grows with longer docs, where a parent is one section rather than the whole file and fixed-size chunks would split more facts.
- Revisit if: ingestion reports metadata-size errors, the answer eval doesn't recover in-09 and in-15, or the corpus grows enough that ~1,000-token parents stop being "about one section" (then revisit parent size or pre-splitting by section).

## Chat: request/response, not streaming

- Status: In use (phase 5a, branch `feat/web-chat-send`). `apps/web/src/components/chat/ChatThread.tsx` and `useSendChatMessage` in `apps/web/src/lib/api/hooks.ts`.
- What it does: The web chat sends a message with one `POST /v1/chat/sessions/{id}/messages` through the generated client and renders the whole assistant answer when the response arrives.
  - **While waiting:** the user's message appears immediately (an optimistic cache entry), Send is disabled, and a status line says the assistant is answering.
  - **Citations:** listed under each answer as `[n]` source file plus snippet, collapsed in a `<details>` element. An answer with no citations renders no citation block.
  - **503:** shows "The assistant is temporarily unavailable.", keeps the typed question, and offers Retry.
  - **404:** says the session is gone.
  - **Other errors:** use the existing problem+json message mapping.
  - **Validation:** 1–2,000 characters after trimming, mirroring the API, which stays the source of truth.
  - **Accessibility:** a dedicated `aria-live` region announces each new answer once, the textarea is labeled, Enter sends and Shift+Enter adds a newline. Nothing is sent mid-IME composition.
- Why we chose it: Answers are short and fast. The live smoke run measured retrieve at 440 ms and Converse at 1,037 ms, about 1.5 s end to end for a full grounded answer. A spinner for about 1.5 s is acceptable, and request/response keeps every existing piece unchanged: the generated client, problem+json errors, the static-export frontend, the API's synchronous route and its tests, and storing the whole answer with its citations in one write. Citations are filtered from the complete answer text (only `[n]` actually cited), which is simplest when the whole answer is in hand.
- Rejected alternative: Server-Sent Events streaming (Converse's `ConverseStream`). Text would appear incrementally, but it needs a streaming endpoint and client, a different error model mid-stream (a 503 after half an answer), citation filtering only at the end, a second storage path for partial answers, and proxy and CloudFront configuration that buffers or times out streams. That's a lot of moving parts to save about 1 second.
- Tradeoff we accept: A spinner instead of incremental text. If answers get longer, or latency grows (bigger parents, larger models), the wait becomes noticeable. Retrying after a 503 is idempotent: see "Idempotent message send".
- Revisit if: p95 end-to-end latency rises past about 3 s, answers routinely run several paragraphs.

## Idempotent message send

- Status: In use (branch `fix/chat-idempotent-send`). `POST /v1/chat/sessions/{id}/messages` requires `client_message_id` (UUID). Implemented in `ChatRepository.store_question_once` and `store_answer_once`; the web client is `ChatThread` / `useSendChatMessage`.
- What it does: The client generates one `client_message_id` per question and reuses it when retrying that question. On the server, per (session, `client_message_id`):
  - **First send:** a single DynamoDB `TransactWriteItems` writes three things together: a `REQ#<client_message_id>` idempotency item (with `ConditionExpression: attribute_not_exists(PK)`, the user message's id, and a SHA-256 of the content), the user message itself, and the session's `last_message_at` / TTL update.
  - **Repeat send:** the condition fails, the whole transaction is cancelled, and nothing is written. The repository then reads the `REQ#` item:
    - **An answer is already linked:** it's returned with no retrieval or model call.
    - **No answer yet** (the first attempt hit a 503): retrieval and generation run again, without storing a second question.
    - **The same id arrives with different content:** 409, since that's a client bug, not a retry.
  - **Recording the answer:** a second transaction puts the assistant message and links it from `REQ#` with the condition `attribute_not_exists(assistant_message_id)`. If two retries race, only the first answer is stored, and the second request gets that one back.
  - **Storage details:** `REQ#` items live in the session's partition (so ids are scoped per session), carry the same sliding TTL as the session, and sit outside the `MSG#` prefix, so message listing never sees them.
- Why we chose it: The API stores the question before calling Bedrock, deliberately, so a 503 still leaves a record of what was asked. Without a key, Retry stored it again (Incidents, "Retry after a 503 duplicates the user's question"). A conditional put inside the same transaction as the message is atomic: there's never a stored question without its idempotency item, and two concurrent sends with the same id can't both win, because DynamoDB evaluates the condition and the writes as one unit. Linking the answer from the same item lets a retried success return the original answer, so a client retry can't double the Bedrock cost.
- Rejected alternative: Storing the question only after a successful answer. That's no duplicates for free, but a 503 would leave no trace of what the seller asked, which loses the "the thread shows what was asked" property the route was designed around. Also rejected: a separate "regenerate" endpoint for retries. It's an explicit verb, but the client then has to know whether the first attempt stored anything (unknowable after a timeout), and it adds an endpoint, a contract and tests for a case the key handles transparently. Also rejected: deduplicating by content. Two genuinely separate identical questions are legitimate, and a client-chosen id makes intent explicit.
- Tradeoff we accept:
  - **A required field** in the request contract: clients must generate and keep a UUID per question, and a missing or invalid id is a 422.
  - **More writes:** one extra item per question, and a conditional write plus a follow-up read on replays.
  - **Different transaction shapes:** sending is two transactions (question, then answer) instead of two plain appends, and replay handling reads `CancellationReasons`.
  - **Wasted generation in a race:** if two retries run concurrently before either records an answer, both call the model and only the first answer is kept.
- Revisit if: clients need cross-session or cross-device dedup (then the key needs a different scope), or replays become common enough that the follow-up read matters.

## No self sign-up (invite-only Cognito users)

- Status: Defined in CDK (6a). `AuthStack` sets `selfSignUpEnabled: false` (`AllowAdminCreateUserOnly: true`), pinned by a Jest test that was negative-tested.
- What it does: Nobody can create their own account. An operator creates each user with `make auth-create-user EMAIL=... GROUP=seller|admin`. That target calls `admin-create-user` with `--message-action SUPPRESS`, reads a temporary password with echo off and sends it on stdin (never echoed, never in a file or argument list), then adds the user to the group. Users set their own password at first sign-in. A seller user is then linked to a seller row with `make link-user`.
- Why we chose it: Every signed-in seller can ask the chat, and every question costs Bedrock tokens. Open sign-up would let anyone on the internet create accounts and spend money on retrieval and generation, and there's no rate limiting yet ("Cut or deferred": rate limiting deferred). This is a demo with a handful of known users, so invite-only matches reality and caps spend.
- Rejected alternative: Open self sign-up with email verification. Lower friction, but it invites bot sign-ups and abuse of the Bedrock-backed chat, and a seller account also needs a matching `sellers` row, which self sign-up wouldn't create anyway.
- Tradeoff we accept: Every new user needs an operator with AWS credentials. There's no "Sign up" link on the hosted UI.
- Revisit if: There's a real onboarding flow (seller verification, billing), together with rate limiting on the chat endpoint.

## TOTP-only MFA

- Status: Defined in CDK (6a). MFA `OPTIONAL`, enabled MFA type `SOFTWARE_TOKEN_MFA` only, pinned by a Jest test.
- What it does: Users can enrol an authenticator app (TOTP) as a second factor. SMS MFA isn't enabled, and the pool has no SMS configuration or SNS role.
- Why we chose it: TOTP is free and works on the Lite plan ("MFA with authenticator apps and SMS one-time codes" is Lite, Essentials and Plus: https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-sign-in-feature-plans.html#cognito-sign-in-feature-plans-list). SMS MFA is billed per message through Amazon SNS, outside the MAU price (https://aws.amazon.com/cognito/pricing/), and needs an IAM role for Cognito to publish to SNS. That means more cost, more IAM and more execution-policy surface, plus SIM-swap risk.
- Rejected alternative: SMS MFA, for the cost, IAM and security reasons above. Also rejected: making MFA required, which is friction a demo with invited users doesn't need yet.
- Tradeoff we accept: MFA is optional, so accounts without TOTP rely on the password alone, under a strong policy (12+ characters, upper, lower, digit and symbol). There's no fallback factor for users without an authenticator app.
- Revisit if: Real sellers onboard (then make MFA required), or a user population can't use authenticator apps.

## Local live run against real AWS (`make live-env`, `make dev-live`)

- Status: In use (branch `docs/local-live-run`). Runbook in README, "Run against real AWS".
- What it does: Runs the web app and API on the developer's machine against the deployed Cognito user pool and Bedrock Knowledge Base.
  - **`make live-env`** writes the gitignored `services/api/.env` and `apps/web/.env.local` from the stack outputs. It writes no AWS credentials, and backs up any file it replaces.
  - **`make dev-live`** starts only Postgres and DynamoDB Local in Docker, runs migrations and table init, seeds once (only when `sellers` is empty), then runs the API on the host (`uvicorn`, port 8000) with the developer's `aws login` session for Bedrock.
  - **DynamoDB Local now runs with `-sharedDb`.**
  - **`make auth-create-user`** now uses a small boto3 script (`scripts/cognito_create_user.py`): the password is read with `getpass` and sent in one `AdminCreateUser` call.
- Why we chose it: It's the shortest path to a real end-to-end run (Cognito sign-in, then the API, then Bedrock RAG) without deploying the app.
  - **API on the host, not in a container:** the host process can use the developer's short-lived `aws login` credentials, and building the API image needs Docker Hub, which was unreachable locally.
  - **`-sharedDb`:** DynamoDB Local otherwise keeps a separate database per access key. The make targets create the table with dummy keys, and the API's real session keys rotate, so without it the API would never see the table.
  - **boto3 for user creation:** the AWS CLI can't take the password on stdin (see Incidents, "make auth-create-user failed"). boto3 with `getpass` keeps the password out of argv, files and the terminal, behaves the same in zsh and sh, and rejects an empty password before any AWS call.
- Rejected alternative: Running the API container with the developer's credentials mounted or passed in (needs Docker Hub, and leaks long-lived credential handling into compose). Passing the temporary password as `--temporary-password` (visible in `ps`). A FIFO for `--cli-input-json` (the CLI reads the source twice: the second open blocks forever).
- Tradeoff we accept:
  - **The local API runs with the developer's full AWS permissions,** not a least-privilege runtime role (listed under Known open issues).
  - **`-sharedDb` means every credential sees one local database.** That's correct for local dev; CI's service container is separate.
  - **`make auth-create-user` now needs the API's virtualenv** (`uv`).
- Revisit if: The app is deployed to AWS (the runtime then uses a task role, and this runbook becomes dev-only).

## sessionStorage for tokens (not memory, not cookies)

- Status: In use
- What it does: `oidc-client-ts`'s `WebStorageStateStore` persists the access and ID tokens to `sessionStorage`.
- Why we chose it: Survives a page reload (an in-memory-only store would force a fresh login on every refresh, which is a bad experience for a page the user reloads often) but clears when the tab closes, unlike `localStorage`, which would leave tokens sitting around indefinitely.
- Rejected alternative 1: In-memory only (a module-level variable, no storage API). Best XSS resistance, since nothing durable exists for a script to read, but every page reload would force a full Cognito hosted-login redirect, which is disruptive for a page reloaded as often as this one likely is.
- Rejected alternative 2: An httpOnly cookie set by a server. Immune to XSS token theft entirely, but this app has no server component (static export to S3/CloudFront); setting an httpOnly cookie needs a backend to set it, which would mean standing up a server whose only job is auth.
- Tradeoff we accept: `sessionStorage` is readable by any script running on the page, so a successful XSS attack can exfiltrate the access token for that session. The CSP (`<meta http-equiv="Content-Security-Policy">` in `layout.tsx`) is the primary mitigation: it restricts `script-src`/`connect-src` so an injected script has nowhere to load from or send data to. This is a real, accepted risk given the static-export constraint, not an oversight.
- Revisit if: The app grows a server component (even a thin one) that could set httpOnly cookies, or a stored-XSS vector is found in the app's own rendering that this CSP wouldn't already block.

## ResponsiveTable: one data source, two renderings

- Status: In use
- What it does: `ResponsiveTable` takes one `columns`/`rows` pair and renders both a real `<table>` (shown `md:block`, hidden below `md` via the `hidden` utility) and a card `<ul>` (shown below `md`, hidden at `md:hidden`) from that same data, rather than each page hand-writing a separate mobile layout.
- Why we chose it: A hand-written mobile view kept in sync by hand with its desktop table is a change every page has to remember to make twice; deriving both from one `columns` array makes that drift structurally impossible; a new column shows up in both renderings automatically.
- Why `hidden`/`md:hidden` (display:none) and not a visually-hidden (`sr-only`, clip-based) approach: `sr-only` only hides content visually and leaves both copies in the accessibility tree, so a screen reader user would hear every row announced twice (once from the table, once from the card list) even though a sighted user sees only one. `display: none` removes the inactive copy from the accessibility tree entirely, so exactly one rendering is exposed at any given viewport width, for both sighted and screen-reader users.
- Rejected alternative: Two separate components per page (a `<table>` and a card list, each hand-written). More direct to read for any one page, but doubles the work and the chance for the two to drift, and both add up across the six pages that list something.
- Tradeoff we accept: Both renderings exist in the DOM at once (only one is visible via CSS), which means slightly more markup shipped than a media-query-free approach, and any interaction handler on the first column (`rowHref`) has to be wired identically in both branches of the component.
- Revisit if: A page's mobile card layout needs to diverge meaningfully from "first column as title, rest as label/value pairs" (a genuinely different mobile UX, not just a reflow).

## Hermetic AWS environment in tests

- Status: In use (`services/api/tests/conftest.py`, guarded by `tests/unit/test_aws_isolation.py`)
- What it does: The top-level test conftest forces dummy `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`, sets `AWS_DEFAULT_REGION=us-east-1`, unsets `AWS_PROFILE` / `AWS_DEFAULT_PROFILE`, and points `AWS_CONFIG_FILE` / `AWS_SHARED_CREDENTIALS_FILE` at a path that doesn't exist, before any test module imports boto3. A guard test asserts boto3 resolves exactly those dummy env credentials.
- Why we chose it: Tests must never be able to sign a request as a real AWS identity, and must behave the same on a laptop with a live AWS login as in CI. Env-var credentials are first in botocore's provider chain, so forcing them there (and hiding `~/.aws`) cuts off every later provider (profile, SSO, `login`, IMDS) in one place, with no per-test fixture to forget.
- Rejected alternative: Adding `botocore[crt]` as a dependency to make the test failure go away. That would let tests successfully resolve the developer's real credentials, which is the actual bug. (Phase 4c later added `botocore[crt]` as a **dev** dependency for a different reason: so the live eval and smoke scripts can use an `aws login` session without exported keys. Tests are unaffected, because this conftest still forces env-var dummy credentials, which sit first in the provider chain, and the guard test still asserts `method == "env"`.) Also rejected: relying on CI's job-level dummy env vars (the status quo), which protects CI only and leaves every local run exposed.
- Tradeoff we accept: The conftest overwrites any AWS env vars exported in the shell, so a test can't deliberately use real AWS (e.g., a live Bedrock smoke test) without opting out explicitly. That's intended: anything that talks to real AWS belongs outside this suite and gets run by hand.
- Revisit if: We add a deliberately live-AWS test tier; it should live in its own directory/marker with its own conftest, not weaken this one.

## Incidents

### 2026-10-28: Backend test suite read real local AWS credentials

- Symptom: Plain `uv run pytest` in `services/api` failed at collection with 3 errors (`tests/integration`, `tests/unit/test_cors.py`, `tests/unit/test_health.py`): `botocore.exceptions.MissingDependencyException: Missing Dependency: Using the login credential provider requires an additional dependency. You will need to pip install "botocore[crt]"`. CI stayed green throughout.
- Root cause: Nothing in the test suite isolated AWS credential resolution. With no AWS env vars set, botocore walked its provider chain into the developer's real `~/.aws/config`, which uses the `login` provider (needs `botocore[crt]`, not installed). CI passed only because `.github/workflows/ci.yml` sets dummy `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` at job level, and the Makefile's `migrate`/`dynamodb-init` targets set them inline, so the gap only showed on a machine with a real AWS login. Had `botocore[crt]` been installed, tests would have silently resolved a real IAM user's credentials.
- Evidence: Repo audit on 2026-10-28 reproduced the collection error with no AWS env vars in the shell; the same suite passed (83 tests, 90% coverage) once dummy AWS vars were exported. On `fix/hermetic-tests`, `tests/unit/test_aws_isolation.py` fails with the same `MissingDependencyException` when the conftest fix is commented out, and passes with it restored.
- Fix: `services/api/tests/conftest.py` forces dummy AWS credentials, unsets `AWS_PROFILE`, and points the AWS config/credentials files at a nonexistent path before any boto3 import; `tests/unit/test_aws_isolation.py` asserts boto3 resolves only those dummy env credentials. Did not add `botocore[crt]` (see "Hermetic AWS environment in tests").
- Lesson: "CI is green" proved only that CI's environment was hermetic, not the suite. Isolation belongs in the test code itself, with a test that fails if it regresses, rather than in whatever env vars the runner happens to set.

### 2026-10-29: Local `npm ci` failed on a non-writable npm cache; commit pushed before final verification

- Symptom: During phase 4b's final pre-commit check, `npm ci` in `infra/` failed (`EACCES: permission denied, mkdir '~/.npm/_cacache/content-v2/sha512/c6/83'`, reported as `EEXIST`). It had already deleted `infra/node_modules`, so the next step failed with `sh: tsc: command not found` and synth exited 1. The commit (`072fffa`) and push still ran, because the verification and commit commands were chained with `;` rather than `&&`.
- Root cause: Two separate faults. (1) Environment: part of the local npm cache under `~/.npm/_cacache` isn't writable by the current user, most likely root-owned files left by an earlier `sudo npm`. ### 2026-10-29: Retry after a 503 duplicates the user's question (open bug, now on `main`)
